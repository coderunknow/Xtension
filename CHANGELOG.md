# Changelog

All notable changes are listed here. Versions follow SemVer. The version in `VERSION` is the single source.

## [0.1.0-dev5] - 2026-10-18

Prerelease. Windows x86/x64, .NET Framework 4.8, C# 5. No runtime dependency added.

- Bind close validation to the displayed tab's UIA runtime identity, not only its coordinates. Missing or changed identity refuses closing, including replacement at identical geometry.
- Require Chromium tab items to be children of the UIA tab list; unimplemented catalog entries refuse at the scanner boundary too.
- Make settings writes transactional across disk and cache. Failed writes/invalid batches cannot leak into later saves; reject line injection and oversized output.
- Keep controller snapshots isolated and synchronize appearance/language/enabled values through the established settings path.
- Marshal scan-trigger state onto the UI thread, ignore unrelated system events and include close-lane timing in diagnostics.
- Add opt-in Chrome after independent actual-EXE acceptance in both architectures. Edge failed the unchanged depth cap on restart and is explicitly disabled; real Edge refusal is tested, not called support. Existing installations remain Brave-only.
- Use the published dev4 EXE, checksum-verified on the Windows runner, for the resource baseline. Do not silently skip failed latency samples.
- Cancel held presses on overlay placement/identity replacement; repair same-window UIA event resubscription and keep backup-import results visible. Report real per-lane scan/queue timings.
- Export/import bounded unknown future settings as well as known keys; clarify defaults, clamping and backup privacy in both languages.
- Owner reports historical audio distortion is no longer observed; no causal fix claimed and sound-free notices are retained.

See `docs/DEV5_AUDIT.md` for evidence, acceptance state and remaining risks.

## [0.1.0-dev4] - 2026-10-16

Prerelease. Windows x86/x64, .NET Framework 4.8, C# 5. No runtime dependency added. No published tag, release or asset
was replaced.

### Added

- **Browser provider boundary.** `BrowserCatalog` describes each browser as data: exact executable name, display name in
  both languages, and the tab-access contract the scanner needs. A window is only scanned when the foreground process
  image name matches a browser whose contract is implemented *and* which the user enabled. Brave is the only browser
  with acceptance evidence; Chrome, Edge and Firefox are listed with their executable name, their intended contract and
  an explicit `unsupported` support level, so they are discoverable and are never advertised as working.
- **Performance profiles** (`performanceProfile`): `balanced` (the dev3 cadences, and the default), `fast`,
  `low-resource` and `custom`. A profile selects the scan interval, the foreground poll interval, the hover poll
  interval and the dashboard scan interval — nothing else. It cannot change a scan budget, a deadline, a staleness
  window, a cooldown or a confirmation rule.
- **Appearance settings:** button colour (`dark`, `red`, `blue`, `green`), an optional border, and button opacity
  (30–100%). Opacity is applied as uniform window alpha, so the hit area is exactly the same at every value and even
  the faintest setting is still visible; the × stays fully opaque with a border by default. No appearance value can
  move the button outside the confirmed tab or make an invisible button clickable.
- **Settings backup and restore** (Settings → Advanced): export writes a small JSON document carrying the schema
  version and the settings it understands; import validates and bounds the file, reports which values were applied,
  rejected or preserved, and restores the previous file if the write fails. An export contains only the keys of the
  settings file — no titles, no URLs, no log content, no machine identity.
- **Application icon:** a reproducible multi-size `assets/xtension.ico` (16/20/24/32/40/48/64/128/256, all 32-bit)
  generated by `tools/generate-icon.py`, embedded as the executable's own icon (`/win32icon:` in both build scripts and
  `<ApplicationIcon>` for MSBuild) and as the managed resource the tray and the windows load (`/resource:`,
  `Xtension.AppIcon.ico`). The tray keeps a painted fallback for a missing resource, and both the startup log line and
  the Windows harness report the source and the frame count. No image library was added.
- **Diagnostics for the real-time path:** per-lane scan counters (requests, refused, completed, stale, discarded,
  errors, stalls), scan, queue and event-to-visible percentiles in a bounded buffer, the current state separated from
  the last scan result, the active profile and the effective configuration, and one copyable, sanitized report.
- `docs/DEV4_AUDIT.md`: the whole-repository audit for this candidate — findings with severity, evidence, root cause,
  remediation and regression coverage, the ×-latency trace, the unchanged safety invariants, the audio finding, the
  exact multi-platform blockers, and the unverified surface.

### Changed

- **One scan lane per purpose.** A request now carries `ScanLane.Overlay`, `ScanLane.Close` or `ScanLane.Dashboard`, so
  a background dashboard scan cannot delay the scan that makes the × appear, and close validation is measured on its
  own.
- **A tab switch no longer waits for the interval.** The hover pointer arrival already forced an immediate scan; a UI
  Automation selection event and a foreground change now request an immediate scan as well, with an 80 ms floor and
  polling kept as the fallback when a provider denies, hangs or stops sending events. The event sources can only ask
  for an earlier scan; they can never authorise one, and a hanging registration is abandoned after 1.5 s.
- **Notifications are Xtension's own window.** A Shell balloon is owned by the shell, activates, and can play the
  system notification sound. The notice is now a non-activating (`WS_EX_NOACTIVATE`, `WS_EX_TOOLWINDOW`), sound-free
  window with a bounded auto-close, and the tray tip path uses it instead of a balloon.
- **The settings window is grouped** into General, Appearance, Performance and Advanced, in both languages, with
  controls that follow text scaling and a narrow window. Every control shows the value the app is actually using:
  applying a profile writes the preset's interval into the box immediately, and editing any profile-controlled value
  switches the profile to `custom` on the spot instead of silently keeping the preset's name.
- The static gates now also check the icon frames and their offsets, the executable-icon flags, and that no document in
  the repository claims a platform that has no implementation.

### Fixed

- **`Tick()` lost a whole interval for every refused scan.** The "last scan request" timestamp advanced before it was
  known whether the worker accepted the request, so a request refused because a scan was still running, or because the
  foreground browser was disabled or unsupported, cost a full extra interval. The timestamp now advances only when the
  request was accepted, and refusals are counted separately and reported as `refused=`.
- **An empty browser selection silently meant "Brave".** Clearing every browser box produced an empty mask that the
  loader read as "use the default". An empty mask now keeps the previous selection with a warning, the settings window
  refuses to clear the last browser, and diagnostics can report that no browser is enabled.
- **A backup import reported preserved values it never wrote.** The import result now carries the values of unknown
  keys, and the import writes the ones the backup carries while leaving keys that only the store knows untouched.
- **An unreadable settings file was silent.** A failed read now writes one throttled warning naming only the exception
  type, so a reset-looking settings window has an explanation in the log.
- **The dashboard could show an old result as the current state.** The report is rebuilt from the live snapshot on every
  refresh, and the current state is labelled separately from the last scan result.
- **The statistics line could be missing.** It is now written at most every 15 s or every 50 completed scans, never
  while nothing has been scanned, and it carries the sample count, so a short measurement window contains real numbers
  instead of an empty line.
- The tray icon was painted at run time in a single size and the executable had no icon at all; both now come from the
  shipped multi-size asset.
- **The settings window offered no browser list at all.** `BuildBrowsersGroup` was written and never called, so
  General, Appearance, Performance and Advanced were built and the browsers group was not: the checkboxes existed
  nowhere, the browser mask could not be changed from the window, and the help text describing them was shown next to
  nothing. The group is now built with the others, which is what the harness assertion `the browser list is offered in
  the window` checks. This defect is present in the published dev3 window as well.
- **Two unrelated groups of radio buttons unchecked each other.** The visibility-mode options, the colour options and
  the profile options all lived in one container, and Windows Forms makes radio buttons mutually exclusive by their
  parent container. Loading a hover-mode configuration checked the mode and then the colour, which silently turned the
  window - and the applied setting - back to `always`; a user who picked a colour lost the mode they had just chosen.
  Each logical group now has its own row, the harness selects the mode, then the colour, and then requires the mode to
  survive, so the pairing cannot return unnoticed. This defect is present in the published dev3 window as well.
- **Option rows were clipped rather than wrapped.** At 150% text in the smallest supported window an option measuring
  348 px sat inside a 323 px column and was cut off at the edge; the rows now wrap, and the longest option labels are
  short names (`Balanced`, `Fast`, `Low resource`, `Custom`, `Always when safe`, `Hover over the tab`, `verified`,
  `experimental`, `not supported`) with what the parentheses used to explain moved into the help text that already
  wraps. The layout assertion now reports the clipped control's own text and parent, so the next report names the
  option instead of printing coordinates.

### Performance

- **Where the delay was.** The × path cost three things: waiting out the scan interval when the pointer arrived in the
  tab strip (fixed in dev3 and further reduced here), waiting up to an interval for a tab switch that no timer could
  see, and the UI Automation scan itself. The third is not a code cost and is now measured instead of guessed at.
- **How it is measured, and on what it is measured.** The Windows harness measures a *shipped* EXE: time to its own
  readiness line, idle CPU, working set, private bytes, handles, how many state lines it wrote while sampled, the scan
  cost of the same scanner against the same fixture window, pointer-entry-to-visible latency, and ten real-browser scan
  samples as p50/p95/max. The statistics line adds the product's own counters and timings (`scanMs p50/p95/max`,
  `queueMs p95`, event-to-visible). The CI performance job runs the published `v0.1.0-dev3` binary and this candidate
  in one job on one runner, so the comparison is not across machines.
- No safety rule was traded for speed: the scan budget, node/depth/sibling limits, staleness window, stall threshold,
  close-validation deadline, cooldown, epoch rule and confirmation rules are unchanged.
- **The numbers now exist** (CI run `38921338899`, x64 job `117042083952`, published `v0.1.0-dev3` binary and this
  candidate on the same runner, 20 s sample each, pointer not moved so `events=0` and event-to-visible is `n/a`):
  candidate `startupToReadyMs=108 idleCpuPercent=1.30 workingSetMb=46.5 privateMb=33.8 handles=408
  uiaScanMsP50=12.2 uiaScanMsP90=15.8`, and its own counters `requests=30 completed=30 refused=0 stale=0 errors=0
  stalls=0 scanMsP50=12.0 scanMsP95=17.0 scanMsMax=54 queueMsP95=0.0 samples=30`; published dev3 in the same job
  `startupToReadyMs=104 idleCpuPercent=2.02 workingSetMb=48.7 privateMb=35.3 handles=375 uiaScanMsP50=33.7
  uiaScanMsP90=46.1` (it writes none of the counters, so its latency fields are `n/a`); idle with no browser
  candidate `idleCpuPercent=0.00 workingSetMb=33.5 handles=325 stateLines=0` against dev3 `idleCpuPercent=0.08
  workingSetMb=31.0 handles=313`. The scan cost and the counters are the product's own; the harness measures the same
  scanner against the same fixture window, and the real-browser numbers below come from the acceptance runs.

### Safety and privacy

- The close path is unchanged: a click still only sends Ctrl+W after a fresh scan of the current foreground supported
  browser window confirms one selected horizontal tab, the click landed inside the × of that tab, the geometry and DPI
  still match, no blocking modifier is held, the epoch is current, the close guard authorises immediately before the
  input, and the cooldown is respected.
- The browser boundary is fail-closed: an unimplemented tab-access contract, an unknown process image, a disabled
  browser or a missing descriptor produces no tabs and no selected tab, so the overlay hides and nothing can be closed.
- Profiles and appearance cannot weaken anything: no profile field reaches a budget, deadline, window, cooldown or
  confirmation rule, and opacity cannot change the hit area.
- Privacy is unchanged: no titles, URLs, page content or raw provider messages in the log, in diagnostics, in the
  backup document, in the CI output or in any artifact. The new evidence lines carry counters and milliseconds only,
  and the release workflow still verifies `SHA256SUMS.txt` before publishing.

  new icon, executable-icon and platform-claim rules. No C# toolchain exists in the authoring environment, so nothing
  was compiled or executed there.
- Compilation, the unit suites, the Windows harness, packaging, the performance comparison and the real-Brave smoke
  are verified by the repository's CI jobs, whose run IDs are recorded in the pull request and in the release notes.
- **CI run `38921338899` (commit `bc999a8`) passed every job**: static checks and unit tests (`95 passed, 0 failed`),
  MSBuild project check, Build x64 and Build x86 (each running the 14-test Windows harness: `14 passed, 0 failed`),
  package provenance and checksums, the baseline-vs-candidate performance job, and the isolated real-Brave smoke on
  both architectures. `Kilo Code Review`, a third-party review app that is not part of the repository's workflow,
  reported `action_required` with "Review could not start because the account has insufficient credits"; CodeRabbit
  passed.
- **Real-Brave acceptance on the shipped candidate EXE** (smoke jobs `117042084021` x64 / `117042084269` x86, Brave

  nodes, overlay placed on the confirmed tab without taking Brave's foreground, three `Ctrl+Tab` switches followed by a

## [0.1.0-dev3] - 2026-10-15

Prerelease. Windows x86/x64, .NET Framework 4.8, C# 5. No dependency added. No published tag or asset was replaced.

### Added

- **Settings window** (dashboard, tray menu, or `Settings ...`): turn the × on/off, choose the visibility mode, set the × size and right inset, set the hover keep-time and the scan interval, switch the interface language, set start-with-Windows, reset to defaults, open diagnostics or the log.
- **Hover mode** (`visibilityMode=hover`): the × is shown only while the pointer is over the confirmed selected tab (or on the button itself), with a bounded keep-time (default 250 ms) so moving from the tab onto the button does not make it vanish. Inactive tabs, the title bar, the page area, the taskbar and other applications never qualify.
- **Configurable × size and position**: 18–40 logical pixels (default 26) and a 0–12 logical pixel right inset (default 3). Painting, window placement, hit testing and close validation all use the same configured values. A size whose square plus the inset cannot fit inside the selected tab hides the button and reports that the tab is too small for it, rather than drawing a button outside the tab.
- **Interface language toggle**: Vietnamese (default) and English. Every user-visible string moved into one table; changing the language relabels the settings window, dashboard, tray menu and overlay in place, and re-renders the explanation of the last scan without waiting for a new scan.
- Own settings file at `%LOCALAPPDATA%\Xtension\settings.ini` with the keys `overlayEnabled`, `visibilityMode`, `buttonSize`, `buttonInset`, `hoverGraceMs`, `scanIntervalMs`, `language`. Unknown keys are preserved. Start-with-Windows stays a per-user registry entry and is not duplicated into the file.
- `docs/DEV3_AUDIT.md`: findings with severity, what was fixed, and the remaining unverified risks.
- A Windows performance job that measures the published dev2 EXE and the candidate EXE in one job on the same runner (startup time, idle CPU, working set, handles, UI Automation scan cost).

### Fixed

- `SettingsStore` re-read and re-parsed the file on every getter call; it now caches values in memory, bounds the file size it will load, clamps out-of-range integers and unknown enum tokens to documented defaults, preserves unknown keys when rewriting, and removes a stray `settings.ini.tmp` after a failed replacement that previously survived forever.
- The overlay performed `SetWindowPos`, a bounds read and a repaint on every scan even when nothing moved. Placement is now idempotent and only repaints when the size changes, while still verifying the native bounds and visibility whenever it does move the window.
- A non-Brave foreground re-opened a process handle on every 250 ms tick; negative verdicts are now cached per window and process id (shorter lifetime), while the path that sends Ctrl+W always re-queries.
- The audit suspected each scan leaked its `CacheRequest`. The compiler refuted that: in .NET Framework 4.8 `System.Windows.Automation.CacheRequest` has no `Dispose`, and the disposable activation object was already released by the existing `using` block. The scope of the investigation and its conclusion are recorded in `docs/DEV3_AUDIT.md`; no change was needed beyond not adding an impossible call.
- The controller built a snapshot and pushed a render on every timer tick even when nothing observable had changed.
- The dev2 wording edge case where a minimized non-Brave window was described as "Brave minimized" is corrected; the wording now requires a Brave identity.
- In hover mode, UI Automation work is skipped while the pointer cannot be inside the tab strip. This can only delay showing the × by one interval and can never authorise a close.

### Performance

- **The × no longer waits out the scan interval.** In `hover` mode the moment the pointer enters the tab strip forces the
  next scan to run on that tick, and while the pointer is inside the strip the loop runs at the documented minimum
  interval instead of the configured one; in `always` mode a window that newly comes to the front is scanned immediately.
  The steady-state cadence, every deadline, the staleness window and every confirmation rule are unchanged, and no extra
  scan is submitted while the pointer is away from the tab strip.
- **Windows open faster.** The settings window and the dashboard add their whole control tree with layout suspended and
  lay it out once, each wrapping label measures its text once per text/width/font instead of once per layout pass, and
  both windows share a small set of fonts instead of creating one `Font` per control. `FitToWorkingArea` no longer
  resizes, relocates and relayouts a window that already fits the working area.

### Safety

- The close path is unchanged: a click still only sends Ctrl+W after a fresh scan of the current foreground Brave window confirms the click landed on the × of the one selected horizontal tab, blocking modifiers are not held, and the foreground window is re-read immediately before injection.
- Every geometry, mode, language and interval change invalidates pending confirmation, so a queued validation can never be applied to a differently sized or differently placed button.
- A value that arrives from a corrupted file, a hostile caller or the registry is clamped to its documented range and never trusted, and the settings window repairs out-of-range values instead of crashing.

### Regression coverage and verification

- Core tests extended: settings persistence (round trip, clamping, malformed values, unknown keys, oversized file, failed replacement, reset), parameterised geometry, hover state machine (enter, leave, grace boundary, tab switch, ineligible state, clock going backwards), string-table completeness in both languages, and close-area follow-up of the configured size.
- Windows synthetic tests extended: overlay resize and idempotent placement, settings-window layout at 100/125/150/200% font scaling, language toggle relabelling in place, host round trip with out-of-range values, and a real Ctrl+W chord sent to a throwaway window that must be delivered in full and leave no key down.
- Real-Brave acceptance extended with a second phase: hover mode visibility and hiding, the configured 40 px button, a click on a hover-shown button closing exactly one tab, persistence across an application restart while Brave stays open, and recovery from a corrupted settings file.
- Verification status for this candidate is recorded with its CI run and tag below.

## [0.1.0-dev2] - 2026-10-14

Prerelease. Windows x86/x64, .NET Framework 4.8, C# 5. No dependency added.

### Fixed

- Explicit UI Automation navigation caching: activated cache requests alone do not populate TreeWalker results. The previous cached-property read could throw and hide the ×.
- Incomplete depth/time scans, unknown selection beside a known selected tab, and tabs too short to contain the overlay now reject safely.
- Late close results expire independently of timer ticks; overlay results recheck foreground, window geometry/DPI and age. Pending close validation cannot re-show the button. Transient identity failures do not remain cached.
- Native placement/visibility failures are observable. Error diagnostics include operation, type, HRESULT and sanitized application frames without provider messages or browsing data.
- Dashboard explanations and action rows grow within a scrollable viewport; diagnostics explanations scroll and can be selected/copied. Changed errors, counts and timings refresh correctly.
- Background wait handles and tray resources are disposed. Failure to obtain single-instance protection refuses startup rather than risking duplicate closures. Build-tool discovery supports 32-bit Windows.

### Regression coverage and verification

- Added pure-core deadline, privacy, ambiguity, geometry and close-guard boundary tests.
- Added Windows synthetic UIA cache/scanner, overlay, diagnostic refresh and scaled-font/layout tests, in x86 and x64. These are NOT real-Brave acceptance.
- CI [38575630606](https://github.com/coderunknow/Xtension/actions/runs/38575630606) passed source checks, 38 core tests, six Windows regressions in each architecture, both builds, MSBuild and packaging/provenance/checksum checks. Final release-commit CI is linked from PR #2.
- **Real Brave smoke passed:** actual x86 and x64 EXEs with official Brave v1.97.56 on Windows OS 10.0.26100.0 at 96 DPI, isolated temporary profiles. Startup with Brave already running, overlay position, three tab switches, two windows, focus away/back, Shift/Alt/Win rejection, mouse close removing only the selected runtime identity, minimize/restore/move/resize/maximize, twelve tabs and a long synthetic title.
- Synthetic UIA reproduces the old `Cached.ControlType` InvalidOperationException / HRESULT `0x80131509`; explicit caching succeeds. This supports the missing-button correction, but the user's exact exception/environment was not captured.
- The layout tests exposed and then verified the correction for a clipped startup control at 200% scaled text in a narrow window. Tests exercise 100/125/150/200% font sizes; these are not physical-monitor DPI certification or a visual diacritics review.
- Not fully accepted: physical mixed-monitor DPI, native 32-bit Windows, rapid physical double-clicks/tab switches during validation, intentionally unsupported tab layouts, real hung-provider behavior, tray/startup registration and graceful shutdown. Core/worker safety tests cover deterministic rejection and recovery, not those complete runtime scenarios. Existing post-validation input race remains documented.
- Optional external code reviews were unavailable (Kilo credits, Qodo trial, Copilot quota; CodeRabbit skipped). No review failure was bypassed or described as a successful review; repository CI passes independently. See `docs/DEV2_AUDIT.md`.
- Packaging now refuses stale/dirty/wrong-version/wrong-architecture binaries using commit/hash provenance and checksums. Release workflow additionally downloads published assets and verifies them.

## [0.1.0-dev1] - 2026-10-14

Prerelease. Windows x86 and x64 only.

### Added

- Custom × on the selected horizontal Brave tab, placed at the tab's right edge and moved when the tab changes.
- Dashboard with status and the reason the × is hidden, a turn-on/turn-off control, and a startup option.
- Diagnostics window listing the tabs from the last scan, with scan time and node count.
- Single-instance protection. Launching again opens the running instance's dashboard.
- Startup with Windows, off by default. Per-user registry entry; no administrator rights.
- Unit tests for the pure core (geometry, tab selection, close guard, clock, settings).
- CI workflow (static checks, unit tests, x86/x64 builds, MSBuild project check) and tag-triggered prerelease workflow.
- Release assets: x86 and x64 EXEs, source ZIP from git archive, SHA-256 manifest, and release notes.

### Changed

- The version is generated from `VERSION` into the C# constants, assembly attributes, and the application manifest.
- Overlay geometry is scaled per monitor DPI. Tab recognition thresholds scale with DPI, so a 200% display is handled.
- Scans run on a dedicated thread at 500 ms intervals with a 1000 ms budget and a 1500-node cap. The UI thread no longer waits on UI Automation.
- Dashboard and diagnostics update only when their content changes, and only while visible.
- Disabling the × and exiting are separate actions. Both warn that native close buttons may stay hidden if Brave's own setting is on.
- Logs contain no tab or window titles.
- `Xtension-v0.1.0-source.zip` is no longer stored in the repository. Source archives are built per release.

### Fixed

- A close click is validated again at click time: foreground window, scan freshness, and the × position. A stale or uncertain state sends nothing.
- A late validation result is discarded after a state change or timeout.
- A stalled UI Automation call hides the × after 5 seconds instead of leaving it clickable.
- The × window no longer takes focus from Brave when shown.
- Brave process identity is cached briefly instead of being queried on every check.
- Keyboard input is refused while Shift, Alt, or Win is held, so Ctrl+W cannot become Ctrl+Shift+W.
- Settings are written through a temporary file and then replaced.

### Security and privacy

- No mouse injection. The close path uses only Ctrl+W through SendInput.
- Per-user startup only; the app requests `asInvoker` and no `uiAccess`.

### Verification

- Static checks, unit tests, x86/x64 builds, and the MSBuild project check run in CI for this tag.
- Not verified: behaviour inside Brave (× placement, click-to-close, DPI, Brave setting interaction, tray and dashboard behaviour). These need manual testing on Windows.
- No performance percentage is claimed. Diagnostics reports scan time and node count so these can be measured on a device.
